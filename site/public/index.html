A rule system for every use case

Block, redirect, challenge, or override matching requests before they reach your service.

  • request
    • rule "scanners"/.env, /.git and the like answered with a 404, never reaching the app
    • rule "limit writes"On /api, anything but GET and HEAD, 60 a minute
    • upstream "api:4000"What's left, forwarded
config.hcl
host "shop.example.com" {
  # Scanners never reach the app
  rule "scanners" {
    and {
      path { contains = ["/.env", "/.git", "/wp-login"] }
    }
    then {
      respond { status = 404 }
    }
  }

  location "/api" {
    upstream "api:4000" {}

    # Reads stay free, writes get a limit
    rule "limit writes" {
      and {
        method { not_in = ["GET", "HEAD"] }
      }
      then {
        rate_limit {
          requests = 60
          per      = "1m"
        }
      }
    }
  }
}

And so fast they barely touch performance. Rules are compiled when the configuration loads and you can add as many as you want.

Everything a proxy in front of your apps needs

Automatic HTTPS

Let's Encrypt certificates, wildcards through DNS challenges, your own files, or Kubernetes secrets.

HTTP/3 and HTTP/2

QUIC for browsers that speak it, websockets over HTTP/2, and HTTP/2 or TLS to your upstreams.

Docker and Kubernetes

Containers found by their labels, and an ingress controller that sends requests straight to pods.

Plugins

Basic auth, JWT, OAuth2, forward auth, CORS, rate limits, waiting rooms, static files, compression.

Traffic

Canary splits, mirrors, retries, health checks and least-connections balancing across your upstreams.

An admin UI

Traffic as it happens, the latest requests, hosts and their rules to change, and Prometheus metrics.
