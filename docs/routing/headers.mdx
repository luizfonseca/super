Super can change the headers of responses (sent to the client) and of requests (sent to the upstream).

## Response headers

Response headers can be added or removed for a whole host or for a single location:

```hcl
host "example.com" {
  # Every response of the host
  headers {
    response {
      add    = { "X-Api-Version" = "2" }
      remove = ["Server"]
    }
  }

  location "/assets" {
    upstream "10.0.0.1:3000" {}

    # Only responses of this location, applied after the host's
    headers {
      response {
        add = { "Cache-Control" = "public, max-age=3600" }
      }
    }
  }
}
```

A location's headers are applied after the host's, so a location can override a header added by its host.

They're also applied to the responses Super sends itself, such as a `429` from `rate_limit`, a `401` from `basic_auth`, or a `502`, `503` or `504` when an upstream fails. A request that matches no location gets a `404` without them, as it has no location to take them from. Super's own responses have no `Server` header.

## Request headers

Headers added to the request sent to an upstream are set on the upstream itself. This is mostly useful for external services that expect a specific `Host` header:

```hcl
location "/" {
  upstream "docs.proksi.info:443" {
    sni = "docs.proksi.info"

    headers {
      add = { "Host" = "docs.proksi.info" }
    }
  }
}
```

The `Host` header of the original request is forwarded unchanged unless an upstream sets it.

## Forwarded headers

Upstreams receive who the client is and how it connected:

| Header | |
| --- | --- |
| `X-Forwarded-For` | The client's address |
| `X-Forwarded-Proto` | `https` or `http` |
| `X-Forwarded-Host` | The `Host` the client asked for |
| `X-Real-IP` | The client's address |

A client's own `X-Forwarded-*` headers are replaced, so it can't pass for another address. Behind proxies listed in `server.trusted_proxies`, their headers are kept and the proxy's address is appended to `X-Forwarded-For` (`X-Real-IP` is then the client they forwarded, as for [rate limits](/plugins/rate-limit)).

They're set before a location's `headers`, which can still change or remove them.

## PROXY protocol

Behind a load balancer working on TCP (such as an AWS Network Load Balancer), every connection comes from the load balancer's address, and it can't add `X-Forwarded-For` to HTTPS it doesn't decrypt. With the [PROXY protocol](https://www.haproxy.org/download/3.2/doc/proxy-protocol.txt), it sends the client's address first on each connection, in a header (version 1 or 2). Super reads it from the load balancers listed in `trusted`, before TLS:

```hcl
server {
  proxy_protocol {
    trusted = ["10.0.0.0/8"]
    # Optional: only on the listeners of these addresses (default: all of them)
    listeners = ["0.0.0.0:443"]
    # Optional: how long a header is waited for, in seconds (default: 5, at least 3)
    timeout_secs = 5
  }
}
```

- The address in the header is the client everywhere Super uses one: `X-Forwarded-For` and `X-Real-IP`, access logs, [`ip_filter`](/plugins/ip-filter), [rate limits](/plugins/rate-limit), and `tcp` blocks.
- Only connections from `trusted` addresses are read. Other clients connect directly to the same addresses, as usual, and a header they send isn't read (an HTTP request starting with one is answered `400`).
- Any machine in `trusted` can claim any client address, so list the load balancers themselves rather than a whole network they share with other machines.
- `listeners` are the addresses hosts and `tcp` blocks listen on: one that's none of them is a configuration error.
- As the protocol requires, a `trusted` address's connections must start with a header: Super never guesses whether one does. One without a header, with a header that doesn't follow the protocol, or without one within `timeout_secs`, is closed. So send headers on every connection of the listeners it's on, health checks included: their headers say they're the load balancer's own (`LOCAL` in version 2), and they're served from its address.
- To serve a load balancer's connections both with and without headers, give them different `listeners`.
- HTTP/3 (QUIC, over UDP) has no PROXY protocol: its clients are the addresses they connect from.
