---
title: "Conditions"
description: "Fields, operators, and how conditions combine."
---

A condition tests a **field** of the request with one **operator**, or combines conditions with `and`, `or` and `not`.

```hcl
host "example.com" {
  rule "api writes from outside" {
    and {
      path {
        prefix = "/api/"
      }
      method {
        in = ["POST", "PUT", "PATCH", "DELETE"]
      }
      not {
        client {
          in = ["10.0.0.0/8"]
        }
      }
    }
    then {
      rate_limit {
        requests = 30
        per      = "1m"
      }
    }
  }

  location "/" {
    upstream "app:3000" {}
  }
}
```

## Combining

| Block | Holds when |
| --- | --- |
| `and { ... }` | every condition inside holds |
| `or { ... }` | at least one condition inside holds |
| `not { ... }` | the one condition inside doesn't hold |

- A rule's condition is always one of these blocks, even when it's a single test: `and { method { eq = "GET" } }`.
- They nest: an `or` can hold `and` blocks, which can hold a `not`...
- A field can appear several times in the same block: `time { gte = "09:00" }` and `time { lt = "17:00" }`, or two `header "x-client"` tests in an `or`.
- `not` holds exactly one condition. To negate several, put an `and` or `or` inside it.
- The order of conditions inside a block doesn't matter: proksi tests cheap fields first and stops as soon as the answer is known.

## Fields

| Field | What it reads |
| --- | --- |
| `method` | the method (`GET`, `POST`...), ignoring case |
| `host` | the host the request is for, without its port, ignoring case |
| `path` | the path, as used to choose locations: `//a/./b` and `/%61/b` are `/a/b` |
| `query "<name>"` | the value of a query parameter, decoded (`a+b` and `a%20b` are `a b`) |
| `header "<name>"` | the value of a request header (several values joined with `, `); names ignore case |
| `cookie "<name>"` | the value of a cookie |
| `client` | the client's address; behind `server.trusted_proxies`, the one they forwarded |
| `date` | the date and time now, in UTC (see [times](#times)) |
| `weekday` | the day of the week now, in UTC: `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun` |
| `time` | the time of day now, in UTC: `HH:MM` or `HH:MM:SS` |

## Operators

Each test has exactly one operator.

| Operator | Holds when the value... | Fields |
| --- | --- | --- |
| `eq`, `neq` | is, isn't, this value | all |
| `in`, `not_in` | is one of, none of, a list | all; for `client`, addresses and networks (`["10.0.0.0/8", "203.0.113.9"]`) |
| `prefix`, `suffix`, `contains` | starts with, ends with, contains this text, or one of a list (`contains = ["/.env", "/.git"]`) | text fields |
| `wildcard` | matches a pattern where `*` is any text (`"/api/*/items"`, `"*.example.com"`) | text fields |
| `matches` | matches a regular expression (`"(?i)bot"` ignores case) | text fields |
| `exists` | is there (`exists = true`), or isn't (`exists = false`) | `query`, `header`, `cookie` |
| `gte`, `gt`, `lt`, `lte` | is at or after, after, before, at or before this value | `date`, `time` |
| `between` | is from the first value (included) until the second (excluded): `["2026-11-21", "2026-11-28"]` | `date`, `time` |

`weekday` takes `eq`, `neq`, `in` and `not_in`.

Text fields are `host`, `path`, `query`, `header` and `cookie`.

Lists can be as long as you need: a list of 100,000 values or networks costs about the same as a list of 5, for every operator taking a list (`in`, `not_in`, `prefix`, `suffix`, `contains`).

**When a value isn't there** (no such header, cookie or query parameter): `eq`, `in`, `prefix`, `suffix`, `contains`, `wildcard` and `matches` don't hold, and `neq` and `not_in` do.

```hcl
host "example.com" {
  location "/" {
    upstream "app:3000" {}

    rule "debug only with a token" {
      and {
        query "debug" {
          exists = true
        }
        header "x-debug-token" {
          neq = "s3cr3t"
        }
      }
      then {
        respond {
          status = 403
        }
      }
    }
  }
}
```

## Times

`date`, `weekday` and `time` read the clock, so a rule can turn itself on and off: a maintenance week, a sale, every night's backups. Combined with `and`, `or` and `not`, they write repeating windows too:

```hcl
host "example.com" {
  rule "nightly backups" {
    and {
      weekday {
        in = ["mon", "tue", "wed", "thu", "fri"]
      }
      time {
        between = ["02:00", "04:00"]
      }
    }
    then {
      rate_limit {
        requests = 10
        per      = "1m"
      }
    }
  }

  location "/" {
    upstream "app:3000" {}
  }
}
```

- **Every time is UTC.** A `date` may end with `Z`; any other offset (`+01:00`) stops the configuration from loading, rather than shifting the window.
- `date` values are `"2026-11-21"` (its midnight), `"2026-11-21T00:00"` or `"2026-11-21T00:00:00"`. `time` values are `"HH:MM"` or `"HH:MM:SS"`.
- `between` includes its first value and excludes its second, so `between = ["2026-11-21", "2026-11-28"]` is the seven days from the 21st to the 27th, and the next window can start where it ends.
- A `time` window can cross midnight: `between = ["22:00", "02:00"]` is 22:00 to 02:00. A `date` window can't end before it starts, and a window that never holds (`time { lt = "00:00" }`) stops the configuration from loading.
- A window opens and closes with the first request after its time, to the second: there's nothing to reload.
- Dates that move every year, like "the fourth Friday of November", are written out for each year.

## Errors

Rules are checked when the configuration loads: an unknown field or operator, a value of the wrong type, an invalid regular expression or network, a test outside an `and`, `or` or `not` block, or two conditions side by side stop it from loading, with the rule's name and the path to the problem:

```text
host "example.com": rule "api writes": and.method.gt: isn't an operator of method (it takes `eq`, `neq`, `in` and `not_in`)
```

## In YAML

The same tree, with `rule` as a list:

```yaml
host:
  example.com:
    rule:
      - name: api writes
        and:
          path: { prefix: /api/ }
          method: { in: [POST, PUT, PATCH, DELETE] }
        then:
          rate_limit: { requests: 30, per: 1m }
    location:
      /:
        upstream: { "app:3000": {} }
```

A field repeated inside a block is a list: `and: { time: [{ gte: "09:00" }, { lt: "17:00" }] }`.

Response fields (`status`, `response_header`) are coming next: rules on the upstream's answer.
